## Backend architecture (important)
- **Supabase is the real backend.** All data access goes through `src/supabase.js` via `QueueService`/`UserService`. Tables/views (`queues`, `queue_members`, `courts`, `daily_checkins`, `profiles`, `active_queues_view`, `live_courts_view`) are defined server-side in Supabase — the schema is NOT in this repo, so column/name assumptions must match existing SQL queries in the services.
- **Canonical user table = `profiles` ONLY (do NOT drop/rename).** `queue_members.device_id` and `daily_checkins.device_id` are FKs to `profiles(device_id)`, and BOTH views (`active_queues_view`, `live_courts_view`) now join `profiles` only. The app reads/writes identity via `profiles` (`UserService.saveProfile`/`getProfile`), and `UserService.ensureIdentity()` guarantees a `profiles` row exists before any check-in so FK never blocks. No dual-write / mirror to any other table — `user_profiles` was dropped for real by `supabase/006_unify_identity.sql`; never reintroduce it.
- **Automation lives server-side in SQL, not in JS.** Files under `supabase/` must be applied manually in Supabase Console (SQL Editor → New query → Run; apply AFTER `001`; all idempotent with `drop ... if exists`/`create or replace` so re-running is safe — no `42710`): `001_auto_call_trigger.sql` (auto-assigns the next ready queue when a court turns `AVAILABLE`; also self-heals `CALLING` courts stuck > 3 min back to `AVAILABLE` + queue → `ON_HOLD` every time the trigger runs; advisory lock `83011`), `002_calling_timeout_cron.sql` (needs `pg_cron` paid Add-on — NOT installed; self-heal in `001` is the fallback), `003_one_card_guard.sql` (DB One-Card Limit via `23505`), `006_unify_identity.sql` (rebuilds `active_queues_view` onto `profiles` only then DROPS legacy `user_profiles`), `007_name_validation.sql` (DB CHECK `NOT VALID` — ชื่อจริงไทยล้วน ← ก-๙ / ชื่อเล่นไทย-อังกฤษ; `NOT VALID` = กันเฉพาะแถวใหม่), `008_auto_call_on_queue_full.sql` (NEW: when a queue reaches 4 members → immediately assign it to an `AVAILABLE` court, no need to wait for a court to free up; advisory lock `83012`; complements 001 which only fires on `court → AVAILABLE`), `009_auto_call_on_queue_resume.sql` (NEW: when a queue's status is updated back to `WAITING` — e.g. admin "กลับปกติ" from `SKIPPED`/`ON_HOLD` — immediately re-assign it to an `AVAILABLE` court instead of leaving it stuck `WAITING`; same lock `83012` as 008 so the two triggers serialize on the same queue and do not fight; added because 008 only fires on `queue_members` INSERT, not on `queues.status` UPDATE), `010_push_queue.sql` (NEW: `public.push_queue` work table — pending push jobs enqueued when a court flips to `CALLING`), `011_on_court_calling_enqueue_push.sql` (NEW: trigger `trg_enqueue_push_on_calling` on `courts` — when `status` becomes `CALLING` it collects the 4 `device_id`s of the queue that was called into `public.push_queue` so the Edge Function below can push to them; advisory lock `83013` so it serializes behind 008/009's `83012` instead of racing the same queue; guards on `old.status <> CALLING` so self-heal reassignments don't double-enqueue). Until applied, the system works but only with manual admin actions.
- **Deploy-order gotcha (006):** the app now reads/writes `profiles` ONLY. `006_unify_identity.sql` rebuilds `active_queues_view` (which joined the legacy `user_profiles`) to join `profiles` and then drops `user_profiles`. Because the view is what shows names in the queue list, you MUST run `006` in Supabase Console BEFORE deploying a new build — otherwise the queue list enqueue blank names until 006 runs. Do not deploy the new build before applying 006.
- **Match results / player stats (013 + 014):** `supabase/013_match_records.sql` creates `public.match_records` (queue_id unique, `player_device_ids` snapshot, `winner_device_ids` ≤ 2 — empty = เสมอ). Admin "จบเกม" REQUIRES selecting winners (max 2, doubles) or pressing "เสมอ" before the court is freed (`AdminView.submitFinishResult` → `QueueService.recordMatchResult` → `finishMatch`). Apply `013` in Console SQL Editor (after 006) before the new build — until applied, "จบเกม" will fail with a missing-table error. **RLS FIX (2026-09-21):** `013` originally left RLS enabled with no policy, so admin "จบเกม" failed with `new row violates row-level security policy for table "match_records"`. `013` now ends with `grant select, insert, update, delete ... to anon, authenticated;` + `alter table public.match_records disable row level security;` (same model as `004`). If the table already exists, do NOT re-run `013` (it starts with `drop table` and would erase records) — run just those two statements in Console SQL Editor.
- **Stats hybrid (014) — do NOT revert to counting match_records as the only source.** `supabase/014_profile_match_stats.sql` adds permanent counters `profiles.plays / wins / draws` and a trigger `trg_apply_match_record_to_profile_stats` (`after insert on match_records` → `update profiles set plays=plays+1 where device_id = any(new.player_device_ids)`, `wins` for `winner_device_ids`, `draws` for all players when `is_draw`) so stats survive even if old `match_records` rows are purged for space. `014` also backfills existing `match_records` into the counters (idempotent — it SETs from a full aggregate, not `+=`). `QueueService.getPlayerMatchStats(deviceId)` now reads the counters from `profiles` first and **falls back to counting `match_records` via `countMatchStatsFromRecords`** if the columns don't exist yet (014 not applied) — keep that fallback, it's the deploy-order guard. `match_records` stays as audit + the `queue_id unique` double-finish guard; old rows may be deleted (no delete trigger, so counters intentionally do not decrement). Apply `014` in Console SQL Editor after `013`.
- Real-time updates use `postgres_changes` channels (`QueueService.subscribeToQueueChanges`, QueueService.js:28). Always `removeChannel` the old channel before subscribing again.
- Queue rules enforced in code + DB: max 4 members per queue; Postgres unique-violation code `23505` means "already in this queue / already in another queue".
- `/admin` is gated by a hardcoded PIN constant (`ADMIN_PIN` in AdminView.vue) + `sessionStorage` flag — not real auth. Do not make it real auth without being asked.

## Identity model
- No real auth. Identity is a `device_id` stored in localStorage key `badminton_local_device_id`; profile is cached under `badminton_user_profile`. Never rely on logged-in identity.

## Gotchas
- **Player-pick lists respect the admin GPS filter (CHANGED 2026-09-21 — this REVERSES the old "Player = Admin, always lists `profiles`" rule).** `QueueService.getAvailablePlayersOnSite(currentDateStr, { gpsFilterOn })` (QueueService.js):
  - `gpsFilterOn: true` → only profiles whose `daily_checkins` row TODAY has `status='INSIDE'` (via `getGpsAvailablePlayers`). People not checked-in today are NOT offered.
  - `gpsFilterOn: false` (admin turned the filter OFF) → every `profiles` row counts as inside the venue.
  - BOTH branches still drop anyone busy in a not-yet-finished queue (`fetchBusyDeviceIds({ skipErrorQueues: true })`).
  - All three call sites pass the live state `{ gpsFilterOn: gpsFilterEnabled.value }`: PlayerView invite modal (`openInviteModal`), AdminView "เพิ่มผู้เล่น" picker (`openAddPlayerPicker`), AdminView "สร้างคิวกลุ่ม" modal (`openAddModal`).
  - **Do NOT re-add a `last_active_at` active-window / `gte` filter to the INSIDE query** — it silently returned 0 rows (older/null values) and emptied every list + the badge. Increase/decrease is driven ONLY by check-in (`INSIDE`) / check-out (`OUTSIDE`) transitions on `daily_checkins`.
  - Each modal re-queries fresh when opened, so admin toggling the filter + re-opening a modal shows the right list immediately.
- **"ผู้เล่นตอนนี้ {n} คน" badge (PlayerView, inside the "สถานะสนามปัจจุบัน" heading).** `loadOnSiteCount` (PlayerView): GPS filter ON → distinct `device_id`s in `daily_checkins` today `status='INSIDE'`; filter OFF → count of all `profiles` rows. It refreshes on a `postgres_changes` channel on `daily_checkins` (`player:daily_checkins_sync`), on the 30 s GPS tick, and whenever `loadGpsFilterSetting` reloads (which also re-runs it on admin toggles). Keep this in sync with the pick-list logic above — same source of truth (`INSIDE` today vs all `profiles`).
- **Estimated-wait countdown (`ในประมาณ MM:SS → รอเรียกประมาณ MM:SS น.`) — identical logic in PlayerView AND AdminView.** `getEstimatedWaitSeconds(queue)`: T = `ESTIMATED_MATCH_MINUTES * 60 * 1000` (20 min); each open court's wall-clock free-at = `now` if `AVAILABLE`, else `(statusUpdatedAt || now) + T` for `IN_PROGRESS` and `CALLING` (fixed wall-clock anchor ⇒ the displayed seconds tick down every tick of the 1 s `now` timer); then every full (4-player) queue ahead of this one (`WAITING`/`SKIPPED`, ordered by `created_at`) consumes +T from the earliest-freed court. Rendering: Player card pill = `รอคอร์ดว่าง · ประมาณ MM:SS น.` / `กำลังจะถึงคิวคุณ`; Player "ลำดับคิว" table waiting cell = `รอเรียกประมาณ MM:SS น.` (`getEstimatedWaitTextShort`); Admin table cell = `รอเรียกประมาณ MM:SS น.`. Non-full queues show `รอคน (x/4)` / `รอคนครบ (x/4)`. The estimate pill/cell MUST only render for queues still waiting (`WAITING` only); a queue already on a court shows `ลงคอร์ต {assigned_court}` for `ASSIGNED`/`IN_PROGRESS` and `กำลังเรียก` for `CALLING` (SAME as the AdminView table status cell) — showing "กำลังจะถึงคิวคุณ" on a queue that is already playing/assigned is a regression (reported 2026-09-21). Do NOT freeze this back to a static number — it must count down each second while any court is mid-match/calling. **THIS SPEC IS CANONICAL: on 2026-09-21 the whole estimate feature (plus the card name `getQueueDisplayName(q.id)` and snake-case `q.assigned_court`) was accidentally lost from PlayerView.vue by an external file overwrite (~11:13) and was re-added from this bullet — if it ever vanishes from either view again, restore it to match this exact description and keep BOTH views byte-identical in logic. Do NOT regress the card title back to raw `{{ q.id }}` (font-mono) or to camelCase `q.assignedCourt`, which shows "ลงคอร์ต undefined".** **THREE-POINT LOGIC LOCK (agreed 2026-09-21): (1) ALL courts run in parallel forever — after a queue takes a court, that court's next free-at = last free-at + T and it competes again by numeric sort (`freeAt[0] += T; freeAt.sort()`); NEVER collapse to a single-court serial chain like "queue_k = queue_{k-1} + 20" — that overestimates once more than one court is involved. (2) Courts freeing OUT OF ORDER is handled naturally — the code only ever cares about each court's free-at number, never court number/name; the next waiting queue always gets whichever court frees EARLIEST (`freeAt.sort((a,b)=>a-b)` + re-sort after every assignment). Do NOT add any A-B-C ordering assumption. (3) The first wave works out as `20 − remaining` per court sorted ascending — keep that. (4) **CLAMP freeAt ONLY to `≥ now` when building the list** — a court can never free earlier than "now": `IN_PROGRESS` → `Math.max((statusUpdatedAt||now) + T, now)` (a match that ran past 20 min = frees immediately), `CALLING` → `Math.max((statusUpdatedAt||now) + T, now + T)` (a just-called queue always counts as a full fresh 20-min match from now, so a stale `statusUpdatedAt` from the server never leaves every waiting queue stuck on "กำลังจะถึงคิวคุณ"). Without this clamp, any court whose `statusUpdatedAt + T` lands in the past poisons the whole simulation to 0 seconds everywhere and the estimate never recovers — that exact bug was reported 2026-09-21 ("ทุกคิวติดกำลังจะถึงคิวคุณ") and fixed in BOTH views on the same day; do NOT remove the clamp or merge `IN_PROGRESS`/`CALLING` back into one `(statusUpdatedAt||now)+T` line.**
- **"กำลังแข่งขัน · MM:SS" match-elapsed timer under the court graphic (PlayerView).** When a court is `IN_PROGRESS`, the status line below the graphic reads `กำลังแข่งขัน · MM:SS`, counting UP from when admin pressed เริ่มเกม (`statusUpdatedAt`); it re-renders every 1 s via the `now` timer (`getPlayElapsed`, PlayerView.vue — same helper exists in AdminView and shows in its status pill next to "กำลังเล่น"). Do NOT drop the `· getPlayElapsed(c)` suffix when touching that status line. (The `CALLING` line intentionally stays plain `เรียกคิว` — no countdown there.)
- Check-in enforces GPS proximity (~60 m) to the venue for all users (both PlayerView and AdminView). There is a `DEV_BYPASS_GPS = false` flag in PlayerView.vue — do not enable it except for local demos. PlayerView also has a UI toggle? No — instead, AdminView has an admin-only "ปิดกรอง GIS" button (writes `system_settings` row `gps_filter_enabled`; both views read it + subscribe via realtime; a PlayerView `DEV_BYPASS_GPS = false` flag remains for local demos only). When filtering is off, every page treats all users as inside the venue — for testing, admin-powered only.

- **Header avatar = shortcut to edit profile (PlayerView).** The avatar in the player header (`PlayerView.vue`) is clickable → on tap it opens the "แก้ไขข้อมูลผู้ใช้งาน" form via `resetPlayer` (same as the "แก้ไขโปรไฟล์" button, which is hidden once the header collapses on scroll).
