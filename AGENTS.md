- `/admin` is gated by a hardcoded PIN constant (`ADMIN_PIN` in AdminView.vue) + `sessionStorage` flag — not real auth. Do not make it real auth without being asked.

## Identity model
- No real auth. Identity is a `device_id`; the profile is cached under localStorage `badminton_user_profile`. Never rely on logged-in identity.
- **device_id เก็บแบบ multi-store ผ่าน `src/services/identity.js` (2026-09-22):** `getOrCreateDeviceId()` on mount reads cookie `badminton_devid` (Max-Age 400 d, SameSite=Lax) → IndexedDB `badminton_identity` → localStorage `badminton_local_device_id` → legacy `badminton_user_profile.deviceId` → generate new `USR-...` only if ALL are gone, then `persistDeviceId()` writes all stores so they resync on every page load. REASON: iOS Safari evicts `localStorage` on tab-close (esp. non-home-screen sites + ITP), which used to regenerate a fresh `USR-` → a new `profiles` row ("ผู้เล่น") → inflated on-site count + unending ghost signups. Do NOT revert to reading/writing ONLY `localStorage['badminton_local_device_id']` in the views — the whole point is the cookie/IndexedDB fallback chain across tab close. Keep `getOrCreateDeviceId` (async, mount), `getDeviceIdSync` + `persistDeviceId` (sync fallback in `saveName`, PlayerView ~1339). **IPHONE-SAFARI REALITY (2026-09-22):** Mac/iPad Safari keep the identity after close/reopen but a plain iPhone Safari tab can still purge ALL three stores (cookie+IDB+localStorage) on tab-close under storage pressure / no Home-Screen install — no client-side store survives a full origin-data eviction. Fixes layered in: (a) site is now PWA-installable (`public/manifest.webmanifest` + apple-mobile-web-app meta in `index.html`) — iOS users must **Add to Home Screen**, which grants durable storage exempt from eviction; (b) `persistDeviceId` fires `navigator.storage.persist()` (honored on installed web apps only); (c) **URL `?bmit=1` shows an alert with `identityDebugInfo()`** (device_id + which of cookie/localStorage/IndexedDB survived + origin) — use it to verify on the bouncing device; doc says to remove the `?bmit` alert when the issue is confirmed closed. Real auth (True stable identity) remains out of scope unless asked (AGENTS policy). **INSTALL-TIP BANNER (2026-09-22, PlayerView only):** when `getOrCreateDeviceIdInfo()` reports a fresh `USR-` was just generated (ALL stores were empty — the symptom of opening through an in-app webview from a scanner app / shared link), AND the view is mobile-sized, AND not already a standalone/installed web app, PlayerView shows a ONE-off full-width emerald banner under the GPS banner: `เปิดเป็นครั้งแรกผ่านแอปอื่นใช่ไหม?` + suggestion to tap Share → "เพิ่มที่หน้าจอหลัก" so the identity persists.
